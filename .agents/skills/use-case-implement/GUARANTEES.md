# Technical guarantees and their evidence

Read the sections relevant to the selected slice before choosing enforcement and integration tests. Apply the existing port's guarantees; examples here are conditional, not new requirements. If enforcement needs a contract change, use step 2 of [use-case-implement](SKILL.md) before implementing it.

## Persistence, scopes and concurrency

- **Representation:** distinguish Entity creation from rehydration. Round-trip meaningful persisted state, including inactive status, revisions and credential generations where present. Persist the transition selected by inner logic without recomputing or substituting a different business decision. Reject corrupt/mismatched results according to the contract.
- **Uniqueness:** use an atomic constraint/operation covering the agreed scope and canonical representation. Exercise competing attempts with distinct connections and assert the declared winner/conflict and final observable state. Map the specific recognized constraint, not every integrity error, to the business result. Distinguish business-key conflict from a generated-ID collision when contracts do; retry only when the promised zero-effect condition holds.
- **Read-decide-write:** identify every mutable decision fact, including independent actor eligibility, related records and predicate facts such as counts/absence. Protect those facts through commit or atomically validate them when accepting the exact transition. Target-row version checking alone may be insufficient. Select locking, conditional writes, isolation or another mechanism based on the actual DB semantics; a `with` block or one port method proves nothing by itself.
- **Scope lifecycle:** implement the declared begin/read/commit/rollback/exit behavior, success acknowledgement, resource release and reuse restrictions. If the port requires explicit commit, scope exit alone must not commit. Observe rollback/no partial effects on pre-commit failure and missing commit. Test commit/exit failures and ensure normal success is not emitted when the contract says acknowledgement failed. Never claim rollback of an already committed effect.
- **Contention:** use the production-compatible database engine with independent transactions/connections and controlled barriers/events to force the relevant race. Verify allowed final states, stale-write rejection and forbidden effects, not merely return values or lack of crashes. Sequential calls and timing sleeps alone do not demonstrate protection. Bound test waits and clean up all resources.
- **Transaction uncertainty:** distinguish guaranteed rollback from unknown commit outcome after a disconnect/timeout. Honor the declared uncertainty and retry policy; do not retry merely because the client did not receive success. Any retry of the whole use case must account for all effects it could repeat.

For coupled credential/state changes, test the promised invalidation barrier across the applicable consumers (issuance, authorization or other enforcement paths). State revision and credential generation may have distinct semantics. If some consumers are outside approved inspection scope, report that limit instead of claiming global invalidation.

## Remote providers and security services

- Implement the supported provider API for the configured version, with appropriate authentication, TLS verification, timeouts and resource cleanup. Keep provider representations outside inner contracts. Do not bypass another owner's API by writing its private database.
- Exercise request method/path, meaningful subject/resource identifiers, serialized data, response validation and error translation through the real adapter. A controlled HTTP server or transport double can prove client behavior under malformed responses, timeouts and recognized failures; it does not prove the actual provider accepts the request or provides a remote guarantee.
- Where permitted, use a provider sandbox/contract test to verify interoperability. If unavailable, label provider compatibility unverified, preserve executable local contract tests and identify the missing evidence. Live calls require approval, scoped credentials and safe test resources; never log tokens, secrets or personal payloads.
- A local transaction does not atomically include HTTP/provider effects. Establish the required partial-effect, reconciliation, idempotency and retry semantics from the contract. Add an outbox/compensation mechanism only when a confirmed requirement justifies it. Bound any retries and test duplicated/uncertain attempts; an idempotency header is not proof that a provider honors it.
- For password/token/cryptographic adapters, reuse vetted libraries and the project's configuration. Test applicable interoperability and rejection cases: wrong secrets, invalid signatures, expiry, issuer/audience/algorithm constraints and malformed claims. Inject time at an agreed seam where needed. Do not invent a cryptographic scheme or assume a mocked token proves verification/revocation works.

## Schema changes and safe environments

- Use the project's migration tool and agreed database ownership. Confirm new constraints, nullability/defaults, index behavior and persisted representations against existing data as well as fresh creation. Database defaults may reinforce inner rules; they do not replace executable creation policy.
- Separate behavior-preserving schema mapping from changed business semantics. For an upgrade, check representative old data, collisions and backfill behavior; surface destructive or irreversible operations and compatibility with still-running consumers. Approve any data transformation rather than silently correcting real records.
- Test fresh installation and the relevant upgrade path in an isolated database when both are in scope. Verify the agreed rollback or roll-forward recovery approach; do not promise a reversible downgrade for an irreversible transformation.
- Confirm test target isolation before migrations, truncation or cleanup. Use dedicated databases/schemas or disposable resources; do not infer safety merely from a variable named `TEST_DATABASE_URL`. Avoid commands that print credentials. Applying migrations to shared/production data, deploying or making destructive external changes requires separate permission.
- Discover engine/version, extensions, configuration and migration commands from approved project sources. Report environment differences that weaken evidence, such as substituting SQLite for PostgreSQL concurrency tests. If the needed environment cannot run, record the blocker instead of weakening the guarantee.
